# EasyView_Md 架构与内存改造结果

日期：2026-10-17。基于 `d282948` 工作区；桌面端 2.1.2、扩展 2.1.6。代码与构建结果位于当前工作区。

## 当前结果

多窗口重启会检查所有窗口，并在检查前等待编辑器同步；任一窗口取消，应用都不会退出。AI 面板和表格组件拥有完整的事件、定时器与销毁边界。AI 响应按请求拥有者路由，文档补丁在编辑器确认并完成同步之后才向工具返回成功。

表格解析通过可终止的 Worker 执行，关闭预览会取消读取和解析；文件展开规模在构造 ExcelJS 工作簿之前检查。跨模式历史、聊天、后台热编辑器和待用快照已有明确的容量策略。Version Guard 的文件指纹采用固定缓冲顺序读取。

## 对照审查问题的实现

| 问题 | 当前实现 |
| --- | --- |
| F01 多窗口重启 | 应用级重启遍历全部窗口；复用窗口确认与保存逻辑；确认期间出现的新修改会再次检查；并发重启请求共用同一任务 |
| F02 AI 面板回收 | 移除 document 点击监听器，关闭设置浮层，取消渲染、滚动、聚焦和设置等待任务，释放消息与附件引用 |
| F03 表格组件回收 | 在现有引擎的事件与定时器注册入口补齐实例所有权；实例销毁时释放全部资源和数据引用 |
| F04 AI 响应广播 | 注册表记录请求对应的编辑器；回复仅交给拥有者；未创建的 Lazy 面板不会因别人的回复而初始化；选图请求也带请求 ID |
| F05 AI 编辑确认 | 每次补丁有独立操作 ID；工具等待接受/冲突结果；编辑器完成文档同步后确认；后台标签保留自己的文档与请求上下文；成功后更新工具的编辑基线 |
| F06 批量指纹 | 顺序流式 SHA-256，64 KiB 缓冲；保留操作确认前后的指纹比较 |
| F07 跨模式历史 | undo/redo 合计最多 32 个快照，Markdown 文本估算最多 8 MiB；淘汰旧状态根 |
| F08 驻留容量 | 后台热编辑器同时受 5 实例和 32 MiB 文本估算预算控制；待用快照受 64 条和 16 MiB 文本预算控制；已投递给活动实例的快照不重复留在待用缓存 |
| F09 聊天与图片 | 消息本体裁剪，模型上下文从消息生成；默认只渲染最近 80 条，可查看更早消息；上传和粘贴在读取前检查图片总量 |
| F10 重型表格解析 | 独立 Worker，转移输入 ArrayBuffer；关闭即取消；解析超时 30 秒；构造完整工作簿前检查解压规模、单元格和合并区域 |
| F11 AI 渲染成本 | 流式渲染间隔 100 ms；后台暂停可视重绘；复用已完成消息的 DOM，只重建有变化的消息 |

## 容量策略

| 对象 | 当前限制与行为 |
| --- | --- |
| 跨模式历史 | undo/redo 合计 32 个快照；Markdown 文本估算 8 MiB |
| 聊天会话 | 最多 200 条消息，正文与推理合计约 1,000,000 字符；裁剪旧消息，保留当前对话 |
| 聊天展示 | 默认最近 80 条，按需加载更早消息；所有常驻消息仍受会话预算控制 |
| 模型请求历史 | 从会话消息生成最近 40 条，移除独立无限增长的历史数组 |
| 流式回答 | 正文和推理合计达到约 256,000 字符时停止并显示容量提示 |
| 图片选择与粘贴 | 每次最多 4 张，总源数据不超过 8 MiB；已发送图片也计入会话附件预算 |
| 桌面热编辑器 | 默认保留 5 个；文档文本估算预算 32 MiB；优先淘汰非活动且不可见实例 |
| 待用文档快照 | 最多 64 条，文本估算预算 16 MiB；正在初始化的大文档快照单独保留，避免丢失初始化内容 |
| 表格解析 | 最多 32 个工作表；单元格数和合并区域面积分别限制为 500,000；单工作表展开数据不超过 32 MiB，解压总量不超过 128 MiB |
| 解析任务 | 30 秒超时；关闭预览中止 fetch、终止 Worker 并释放对象 URL |
| 文件指纹 | 逐文件处理，单个流缓冲 64 KiB |

这些是对应资源的预算，不是整个进程物理内存的硬上限。可见分屏和当前文档不会为了满足后台预算被强制关闭。图片源字节预算也不等于解码后位图的大小。

### 表格打开、编辑、保存和关闭

使用 500 行 × 30 列的 XLSX，通过实际界面修改单元格、点击保存，并用 ExcelJS 从磁盘读回，确认修改已经落盘。随后完成 20 次打开/关闭循环。

表格保存绑定点击时的会话与数据；异步完成只更新同一代界面，保存期间产生的新编辑仍保留未保存状态。

修复前，不编辑的每次循环会稳定增加约 1,273 个 DOM 节点和 580 个事件监听器。当前压力场景包含实际编辑、保存和 Playwright 交互，预热后的记录如下：

| 循环次数 | DOM 节点 | JS 事件监听器 | JS 堆 / MiB |
| --- | ---: | ---: | ---: |
| 5 | 3,922 | 771 | 19.36 |
| 10 | 3,922 | 771 | 19.75 |
| 20 | 3,922 | 771 | 19.92 |

DOM 和监听器没有随循环持续增长。JS 堆存在小幅波动，不能据此宣称所有缓存或全部原生内存已经释放。

另生成 5,000 行 × 30 列表格，实际观察解析 Worker 启动后关闭标签，剩余 Worker 数量为 **0**。

对 24 个 4 MiB 文件，在确认入口返回取消，不执行丢弃操作：

| 指标 | 修复前 | 当前 |
| --- | ---: | ---: |

## 当前架构边界

宿主仍为打开的文档保留规范化正文、磁盘基线和同步状态；VS Code Markdown 编辑器仍使用保持隐藏上下文的策略。工作区中的未保存内容和撤销语义依赖这些状态。当前优化覆盖可安全淘汰的热编辑器、待用快照和无界历史，没有引入冷文档存储或重建 Webview 的新生命周期。

当前流式回答仍会重新解析本条回答，已将频率限制为 100 ms 并复用稳定消息。表格仍在工作规模预算内解析完整工作簿，解析在独立 Worker 中执行；保存序列化在用户保存时惰性加载。以上边界不能解释为已经实现全文增量解析或按工作表懒加载。

表格销毁能力通过同一份构建集成同时用于两端，限定 `x-data-spreadsheet` 1.1.9，并保留依赖许可证。依赖版本或关键源码结构变化时构建会明确失败，要求复核集成，不会静默退回缺少销毁能力的实现。未修改 node_modules 中的源文件。

### F11：尾块内部增量处理与有界重解析

`IncrementalMarkdown` 继续缓存顶层稳定块。未完成尾部超过 1,024 个 UTF-16 字符后，转由 `StreamingMarkdownTail` 维护结构内部状态，避免每次重新解析整个增长中的结构；`StreamingTailDom` 同时消费新增行和文本片段，避免解析优化后仍整体替换尾部 DOM；普通追加也不会把已有尾部容器移除再插入，避免重复挂载整棵子树。

| 结构 | 内部处理方式 |
| --- | --- |
| 未闭合围栏 | 逐字符识别正文、换行和候选闭合标记；已确认正文保存为有界文本片段，仅追加新片段，保留原代码节点；长代码行和长候选闭合标记也不重复扫描已有正文 |
| 列表 | 同级单行子项进入缓存后不再解析，只重解析最后一行；缓存紧列表和松列表两种 HTML，空行后确认新子项时只切换一次松紧状态。嵌套、续段、标记变化及引用定义进入有界检查点路径 |
| 引用 | 可独立判定的纯文本引用行进入内部稳定缓存；含跨行行内语法、嵌套、空引用行或 lazy continuation 时进入有界检查点路径 |
| 表格 | 缓存表头、分隔符和已完成的数据行，只重新解析最后一行；沿用 markdown-it 的对齐、转义管道、行内代码和链接规则。结构变化或超长行进入有界检查点路径 |
| 超长段落与其他有歧义结构 | 在输入长度倍增时生成完整 Markdown 检查点；两个检查点之间按最多 1,024 字符的纯文本片段追加新内容，避免持续重解析长段落 |

单行可变区域上限固定为 1,024 字符；超出后不继续按输入帧重读长行。进入检查点路径只发生一次，之后检查点规模按 2 倍增长，累计完整重解析量受几何级数约束。普通追加不扫描原有全文前缀；无新文本的 UI 刷新也不会再次解析。

稳定前缀保存 tokens、HTML 和 DOM。链接引用定义变化时，正常短尾路径只更新受影响块；长尾在结束校准时统一核对引用环境。流式完成后，使用标准 markdown-it 对仍未冻结的尾部原文进行最终校准，最终 HTML 与一次性完整渲染严格一致，原有稳定前缀不因普通完成事件整体重绘。

未闭合围栏的末尾换行严格按原文处理：没有换行时不合成换行，存在 LF/CRLF 时按 markdown-it 规范化结果保留。代码文本和检查点之间的新文本通过文本节点追加；raw HTML 仍禁用。文本分块避免把 UTF-16 代理对永久拆到不同稳定片段。

2 万 → 4 万 → 8 万字符时，五类输入的新路径耗时和累计解析量均接近线性增长。例如围栏累计解析量为 48,710 → 88,710 → 168,710，列表为 77,330 → 146,309 → 284,392，表格为 91,092 → 174,319 → 340,745；旧路径同期为 3,144,992 → 12,520,000 → 50,040,000。围栏、列表、普通引用和表格在此语料中无需检查点；段落分别使用 5、6、7 次检查点解析。原先“围栏里单个持续增长的代码行”反例也单独测量：当前耗时为 0.322 → 0.604 → 1.197 ms，累计解析量为 48,712 → 88,712 → 168,712，不再随长度翻倍增长约 4 倍。

复现命令：`node tooling/benchmarks/architecture-memory.mjs --streaming`。该入口只刷新基准 JSON 的 `streamingTailGrowth`，保留 F10、同步和文件指纹的既有测量。完整基准入口也复用同一套 F11 测量实现。原先的二次增长反例保留在 JSON 的 `streamingLimitsBeforeTailFix` 历史字段，不代表当前结果。

**当前边界：** 复杂嵌套结构、富文本引用及超长行采用检查点策略，检查点之间的新文字会即时出现，但其 Markdown 格式可能推迟到下一检查点或流式完成；不承诺每个中间前缀都与全量解析实时逐字相同。最终 HTML 的严格一致性不受影响。上述线性结论针对累计送入解析器的字符量及已测语料，不是对 markdown-it 任意病理输入内部复杂度、整条聊天传输或浏览器布局成本的数学保证。本轮已消除原先单结构每帧全量重解析及整体尾部 DOM 替换导致的二次增长。

### F10：按工作表解码与保真保存

ExcelJS 4.4.0 的 `Workbook.xlsx.load()` 没有按工作表随机读取的公开接口。本轮采用 ZIP 条目层面的部分解码：

1. 打开时读取 ZIP 目录、工作簿元数据和关系，得到工作表名称、顺序、实际 XML 路径及活动表索引；此阶段不解码工作表 XML。
2. 在可终止的持久 Worker 中按需构造仅含目标工作表 XML 的子工作簿，交给 ExcelJS 解码；全局共享字符串、样式和必要的工作簿元数据仍由 ExcelJS 加载。其他工作表的 XML 不会在此阶段解压、解码或构造单元格对象。
3. 切表时才请求目标表，保留已经编辑的界面数据；首次只加载活动表，没有活动表信息时加载首张。解码后的 ExcelJS 工作簿不作为每张表的常驻副本保留，Worker 保存展示基线，保存修改表时再从原始条目解码。
4. 保存从原始 ZIP 条目集合开始，只替换真正修改的工作表区域。访问过但未修改的表同样原样保留；组件补充的默认 freeze/autofilter/validation 字段不会误触发重写。未加载工作表、宏、自定义 XML 等条目保持内容字节一致。
5. 修改表按界面基线比较单元格、样式、行高、列宽和合并区域。没有改动的单元格保留原生值/公式；全局样式表追加并重映射新增样式，共享字符串追加并调整索引，原有表使用的索引保持不变。格式修改保留原有数字格式和保护属性。失败或重复保存不会改写原始解析基线。
6. Worker 支持打开、切表、保存请求及逐请求超时；关闭预览会终止 Worker 并拒绝未完成请求。保存继续绑定点击时的预览会话和修订号。

涉及文件：`packages/preview-ui/src/spreadsheet/lazyWorkbook.ts`、`xSpreadsheetBridge.ts`、`spreadsheetWorker.ts`，`packages/preview-ui/src/workers/spreadsheet-worker.ts`，`packages/preview-ui/src/viewers/SpreadsheetViewer.ts`，`packages/preview-ui/src/preview.css`，`packages/preview-ui/tests/lazyWorkbook.test.ts`。

新增 6 项测试覆盖：首次懒加载、重复访问缓存、切换加载、未加载和已加载未修改工作表的逐条 ZIP 内容保真、公式/样式/合并区域/VBA/自定义 XML、修改表中未改动原生单元格、重复保存和恢复原基线、目标表解码时才执行逻辑容量检查、活动表选择、两张修改表的全局样式/字符串索引、原本使用 inline strings 的工作簿往返。

### 5.2(a)：Version Guard 容量和列表窗口

历史缓存最多保留 8 个仓库，每个仓库保留最近载入的 500 条提交；继续“加载更多”时滚动保留当前 500 条窗口，可以刷新回到最新提交。提交文件缓存采用 LRU，最多 16 个“仓库 + commit”条目，避免不同仓库共用 hash 时混淆。面板销毁清空缓存，过期异步结果不会恢复已失效一代的数据，同页历史请求去重。

历史列表、提交文件列表和工作区文件树均采用固定 26 px 行窗口，视口最高 320 px，带前后预取行。目录展开、行操作和提交查看沿用现有逻辑，只为可见窗口创建 DOM。

涉及文件：`packages/editor-core/src/version-guard/VersionGuardPanel.ts`、`guardList.ts`、`guardList.test.ts`、`VersionGuardPanel.test.ts`。

新增 3 项测试：LRU 容量及访问续期；50,000 个文件只创建少于 25 个可见按钮且可滚动到最后一行；连续加载 10 页历史后只驻留 500 条提交，历史和 5,000 文件的提交详情均只渲染窗口，销毁后缓存清空。缓存容量按条目定义，单个提交文件数组的大小仍由宿主查询结果决定，并非整个面板的字节硬上限。

### 5.2(b)：PM/CM 变更范围驱动的同步

PM 路径消费 transaction step maps，标记受影响的顶层节点；序列化缓存以持久节点身份和序列化边界状态为键，保留相邻列表间隔等语义。只重新序列化变化节点，对变化区域求文本补丁。100 ms 同步、历史事务和保存前 flush 使用同一个增量序列化入口。

CM 路径从 `ViewUpdate.changes.iterChanges()` 提取多个替换范围及插入文本，经 `SourceModeController` 传给 `EditorSyncAdapter`。适配器验证这些补丁能否从当前乐观正文得到目标正文；可以验证时直接使用范围，否则计算全量补丁。`DocumentSyncSession` 在没有在途编辑时直接发送已知补丁，避免进入协议层后再次全文求差异。

以下情况保留全量路径：包含全局 table metadata 的表格、需要整文 HTML 表格压缩的内容、模式/快照基线不一致、不能验证的补丁，以及在途编辑聚合或外部变更后的重新对齐。协议仍保留正文字符串和完整结果哈希，未修改 ACK、冲突、修订号及重同步语义；整体同步不是 O(1)。

### 5.2(c)：流式保存指纹

将 FNV-1a UTF-16 哈希状态抽为可追加的 `createContentHasher()`，一次性 `hashContent()` 继续使用同一实现。文件边界用 64 KiB 读取流和 `StringDecoder`，保证 UTF-8 多字节跨缓冲、BOM 和无效字节的结果与原 `readFile(..., 'utf8')` 哈希一致。

每次指纹读取核对打开句柄读取前后的设备、inode、大小、mtime/ctime，以及当前路径指向的文件版本；写前仍进行两次内容指纹核对，写后核对发布内容。元数据可快速发现版本变化，不用它代替第二次内容检查。

涉及文件：`apps/desktop/src/main/application/document/documentFileSystem.ts`、`documentFileSystem.test.ts`，`packages/editor-sync/contentHash.ts`。

新增 4 项测试覆盖 UTF-8 边界/BOM/无效字节、成功保存、旧基线和文件不存在、同大小且恢复 mtime 的并发修改、原子替换后的外部写入；断言该保存路径没有调用完整 `readFile`。

8,000,000 字节文件，三次读取/哈希的基准：

| 指标 | 原路径 | 当前路径 |
| --- | ---: | ---: |
| 耗时 / ms | 201.19 | 165.43 |
| 完整文件缓冲分配次数 | 3 | 0 |
| 单次流缓冲配置 / bytes | 整文件 | 65,536 |
| 文件读取次数 | 3 | 3 |

本项的稳定收益是降低额外缓冲峰值，计时受缓存和系统 I/O 波动影响，不保证每次更快。原有非协作进程在检查与 rename 之间的 OS 竞争窗口仍存在，流式指纹没有把保存变成跨进程 compare-and-swap 事务。
